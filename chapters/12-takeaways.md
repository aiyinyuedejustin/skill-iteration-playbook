# 12. 意义与要点

## 这件事的意义

skill 迭代本质上是把软件工程的老办法搬到自然语言上：先写测试，小步修改，看日志找原因，重构去冗余，发版前跑回归。不同之处在于，被测的对象会随机波动，判分本身可能出错，而且被测的 agent 可能找到评测的漏洞。

研究这边的趋势也指向同一个方向。从 APE、OPRO 靠大量搜索，到 GEPA、ACE 靠读轨迹反思，再到 Agent Workflow Memory 和 Voyager 把经验积累成可复用的条目，方法越来越像一个认真的工程师在做的事：看失败，总结规律，写下来，删掉没用的。自动化程度在提高，但评测集、判官和「这条规则是不是通用」的判断，现在仍然主要靠人。

## 十条要点

1. 先有评测，再改 skill。哪怕只有 3 道题。
2. 分开测触发和正文：不触发的 skill 正文写得再好也是零分。
3. 永远同时跑带 skill 和不带 skill，看差值。
4. 优先判结果和环境状态，不判 agent 说了什么。
5. 断言要有区分度：错误的输出也能通过的断言比没有更糟。
6. 模型判官用二元判断加理由，并用人工标注校准，校准要随迭代重做。
7. 改之前读轨迹，记第一个错误，归类计数，先改最常见的。
8. 规则写做法，不写答案；问一句「没见过这道题的人能从这条规则猜出答案吗」。
9. 每隔几轮安排一轮只删不加；删的标准是留出集分数不掉。
10. 跑一次很贵时：分层跑、轨迹存档、断点续跑，限流和重试交给脚本，不写进 skill。

## 最短的上手路径

1. 拿 3 到 6 道你知道答案的题，不带 skill 跑一遍，记下失败。
2. 带 v1 跑一遍，存下全部轨迹。
3. 读轨迹，归类，挑最常见的一类，写成一条通用做法。
4. 在没用来改的题上再跑一遍，没变差就提交成 v2。
5. 重复，每两三轮剪一次。
