# 8. 剪枝：防止越改越长

每次发现一个失败就加一句，是最自然的迭代方式，也是 skill 变坏最常见的原因。

## 为什么长了会变差

- **指令多了会互相挤**。IFScale 测试了模型同时遵守 10 到 500 条指令时的表现，遵守率随指令数量增加而下降，不同模型下降的形状不同，推理模型撑得最久。
- **位置有影响**。《Lost in the Middle》发现长上下文中间的信息最容易被忽略。IFScale 也发现，在指令数量中等时，靠前的指令遵守得更好。
- **格式这种无关的细节也会影响分数**。Sclar 等人发现，只改分隔符、大小写这类不影响含义的格式，同一模型在某些任务上的准确率差距可以很大。这意味着两个版本之间的小差距，可能只是格式噪声。
- **每一句都占上下文**。Anthropic 的上下文工程文章把上下文当作有限资源，主张用最少的高信号 token 达到目标。

## 怎么找出哪几句在起作用

| 方法 | 做法 | 成本 |
| --- | --- | --- |
| 整段消融 | 一次删掉一节，跑评测，看分数掉不掉 | 节数 × 一次评测 |
| 不带 skill 的基线 | 和不带 skill 对比，看总的差值 | 一次评测 |
| 看轨迹里有没有用到 | 读轨迹，看模型有没有引用或遵守某一条 | 只需读，不需要跑 |
| 断言对照 | 每条规则对应一条评测断言，断言一直通过且不带 skill 也通过，说明这条可能没用 | 需要先有断言 |

评测贵的时候，先用后两种便宜的方法筛出可疑的段落，再对少数几段做真正的消融。

## 删的时候注意什么

- **删的标准是留出集分数不掉**，不是「感觉没用」。
- **合并比删除安全**。好几条规则说的是同一个意思时，合成一条更通用的。
- **把细节移出正文**。按 Agent Skills 的渐进式披露，用得少的细节放进参考文件，正文只留一句「遇到某情况时读某文件」。正文变短，信息没丢。
- **别删过头**。ACE 提醒的简短偏差就是这种情况：压缩得太狠，领域细节没了。删完之后，原来那几道题要再跑一遍。

一个经验做法是每两三轮加内容的迭代之后，安排一轮只删不加。

## 小结

指令越多越难被全部遵守。用便宜的方法找出可疑段落，再做消融；合并和移进参考文件比直接删除安全。
