# 5. 怎么判分

判分决定了你在往哪个方向优化。判法不对，分数越高，skill 可能越差。

## 三种判官

Anthropic 把判官分成三类，各有各的毛病，所以通常组合使用：

| 判官 | 擅长 | 毛病 | 什么时候用 |
| --- | --- | --- | --- |
| 代码判（测试、字符串匹配、状态检查） | 快、便宜、可复现 | 只能判写得出规则的东西，容易判得太死或太松 | 有明确结果可查时，优先用它 |
| 模型判（LLM 当判官） | 能判开放式输出、读轨迹 | 有偏差，要校准，本身也有成本 | 判质量、判过程合规 |
| 人判 | 最可靠，能发现没想到的问题 | 慢、贵、难规模化 | 校准另外两种判官，抽查 |

对 agent 来说，最好的判法通常是看最终状态：测试是否通过、文件是否正确、数据是否真的改了，而不是看 agent 说自己做了什么。

## 断言要有区分度

skill-creator 里的判官提示词有一段很有用的话，大意是：一个弱断言通过了，比没有断言更糟，因为它制造了虚假的信心。它要求判官在判分之外顺便批评评测本身，指出这几种情况：

- 断言通过了，但一个明显错误的输出也能通过（比如只检查文件存在，不检查内容）。
- 观察到了重要的结果，好的或坏的，但没有任何断言覆盖它。
- 断言根本无法从现有输出中验证。

skill-creator 的 benchmark 报告也会标出「这条断言在带 skill 和不带 skill 时都通过，可能测不出 skill 的价值」，以及「这道题方差很大，可能不稳定」。这两类提示值得每一轮都看。

## 让模型判官可信

用 LLM 当判官，有几条被反复验证的经验：

- **二元判断加理由，比打 1 到 10 分好**。Hamel Husain 建议判官只给通过或不通过，并写出理由。分数刻度很难校准，二元判断容易和人对齐。
- **拿人工标注校准**。Shreya Shankar 等人的《Who Validates the Validators?》发现，人在看了模型输出之后，自己的评判标准也会变，称为标准漂移。所以校准不是一次性的，判官提示词和人工标准要一起迭代。
- **注意已知偏差**。Zheng 等人的 MT-Bench 论文记录了位置偏差、啰嗦偏差和自我偏好。做 A/B 两两比较时，交换顺序各判一次。Eugene Yan 的综述整理了更多这类发现。
- **判官看得到参考答案，被测 agent 看不到**。参考答案是判官的工具，不是 agent 的。

## A/B 对比还是绝对打分

| 方式 | 适合 | 注意 |
| --- | --- | --- |
| 绝对打分（每道题判通过与否） | 有明确标准的任务，跨版本追踪 | 标准要固定，否则版本之间不可比 |
| 两两比较（v1 和 v2 的输出哪个好） | 质量难以定义的开放任务 | 要交换顺序，样本少时结论不稳 |
| 带 skill 对不带 skill | 证明 skill 有用 | 每次发版都应该做一次 |

## 一道题要跑几次

模型输出不是确定的，同一道题跑两次结果可能不一样。skill-creator 默认每个配置跑 3 次，报告均值和标准差。实际做法：

- 便宜的题，每题跑 3 到 5 次。
- 贵的题，先跑 1 次找问题，在判断「v2 是否比 v1 好」时再对关键题多跑几次。
- 两个版本的差距小于单个版本自身的波动时，不要下结论。

## 小结

能用代码判就用代码判，判结果和状态；模型判官用二元判断加理由，并持续用人工标注校准；断言要能把错误的输出拦下来。
