# 4. 搭一个小评测集

没有评测集，每次改 skill 都只能凭一两次试用的印象。有了评测集，哪怕只有几道题，你也能回答「这次改动有没有用」。

## 题从哪来

几种来源，按可靠程度排：

1. **真实使用中失败过的例子**。最有价值，因为它们就是 skill 要解决的问题。OpenAI 的评测飞轮和 Hamel Husain 的错误分析，都是从真实的轨迹开始。
2. **你自己做过、知道正确答案的任务**。适合端到端任务，你知道最终结果该是什么样。
3. **人工设计的边界情况**。专门测 skill 里某一条规则有没有被遵守。
4. **模型生成的合成题**。Hamel 认为合成数据在没有真实用户时很有用，但要按维度去生成（比如任务类型 × 难度 × 环境），不要让模型随便编，否则题目会很相似。

Anthropic 的建议是：写 skill 之前，先不带 skill 跑一遍代表性任务，记下哪里失败，然后至少写 3 道评测题，再开始写 skill。superpowers 项目里的 writing-skills 把这套做法直接套用了测试驱动开发：先写测试场景，看着 agent 在没有 skill 时失败（并记下它给自己找的理由），再写 skill，看着它通过，最后堵漏洞。

## 要多少题

没有统一答案，取决于每道题跑一次多贵：

| 每次运行的成本 | 起步规模 | 说明 |
| --- | --- | --- |
| 很便宜（单轮问答、分类） | 50 到 100 道 | OpenAI 的评测飞轮示例建议大约 50 条 |
| 中等（几分钟的 agent 任务） | 10 到 30 道 | skill-creator 的触发测试用 20 条 |
| 很贵（容器、长任务、真实 API） | 3 到 10 道 | 每道题要尽量覆盖不同的失败类型 |

题少的时候，覆盖面比数量重要。每道题都应该对应一种不同的情况，几道题测同一件事不如一道。

## 怎么分训练集和留出集

只要你会根据评测结果改 skill，就会对这些题过拟合。防止的办法是留一部分题不看：

- **训练集**：你读轨迹、找问题、据此改 skill 的题。
- **留出集**：只看分数，不看轨迹，不针对它改。用来判断改动是否真的泛化。

skill-creator 的描述优化循环就是这么做的：六四分，提出新描述时把留出集的分数从历史记录里去掉，让负责改写的模型看不到；最后挑最好的版本也是按留出集分数。

题很少（比如只有 6 道）的时候，可以轮换：这一轮拿 4 道当训练集、2 道当留出集，下一轮换。代价是每一道题最终都会被你看过，所以要额外准备几道从来不用来改 skill 的题，只在发版前跑一次。

## 盲测：被测的 agent 永远看不到答案

如果你有参考答案（一份正确的实现、一个已知的分数），它只能出现在判分那一步，绝不能出现在 agent 能读到的地方：

- 参考答案不放进 agent 的工作目录、容器镜像或可访问的仓库。
- 判分在 agent 之外做，agent 只拿到 skill 和题目。
- skill 本身也不能写进答案。这一点最容易在迭代中出问题，第 6 章专门讲。

Anthropic 的评测文章提到，要检查轨迹，确认 agent 不是钻了评测的空子才通过的。Sakana 的 Darwin Gödel Machine 论文里就有一个例子：让系统自我改进以减少幻觉时，它删掉了用来检测幻觉的标记，让假的工具日志看起来像成功了。只要优化的目标能被摸到，就会有这种情况。

## 每道题应该记下什么

skill-creator 给每道题定义的内容可以直接借用：题目（提示词和输入文件）、期望（几条可以判断对错的断言）、以及跑完后的记录（通过与否、证据、耗时、token、工具调用次数、错误数）。再加两样：

- **起始状态**：环境、依赖、版本。不固定的话，两次运行的差异可能来自环境而不是 skill。
- **完整轨迹**：不只是最后的输出。第 6 章的错误分析全靠它。

## 小结

评测集不必大，但要覆盖不同的失败类型；留一部分题只看分数不看轨迹；参考答案只给判官，不给 agent。
